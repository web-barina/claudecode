**作成：2026年8月**
**対象：Webディレクション業務（自分用リファレンス）**

---

## この資料の使い方

サーバー移行、DNS切替、サイトの本番公開、管理画面まわりで「まず何を確認して、どの順番で作業すればいいのか」を判断するための資料。

過去の案件で実際に起きたこと・詰まったことをそのまま反映している。次に同じ状況になったとき、調査を最初からやり直さなくて済む状態を目指す。

**急いでいるときの読み方**

| 状況 | 見るところ |
|---|---|
| これから案件が始まる | 第2部（着手時のヒアリング） |
| 公開日が決まった | 第9部（当日の段取り）→ 第10部（チェックリスト） |
| 何かおかしい | 第11部（トラブル別 原因早見表） |
| 管理画面のどこか分からない | 第7部（サーバー別ガイド） |
| GA4・GTM・Search Console・サイトマップ | 第12部（計測とSEO） |
| 用語が分からない | 付録A（用語早見表） |

**画面情報の基準日：2026年8月**
サーバー会社のアップデートで、メニュー名・位置・ボタン名は変わる。将来この資料を見るときは、書かれたボタンの位置そのものではなく **「何の設定をするための操作なのか」** を基準に最新画面で探すこと。

# 第1部　全体像 ── 何がどこで管理されているか

## 1-1. 混同しないための4層構造

トラブルの半分は「どの管理画面を開けばいいか分かっていない」ことが原因。まずこの4つを別物として分けて考える。

```text
【ドメイン管理会社】
  ドメインを買った会社。お名前.com、ムームードメインなど
        ↓
【DNS管理元（ネームサーバー）】
  そのドメインのDNS設定を実際に持っている場所
  ★ドメイン管理会社と同じとは限らない（Cloudflare等が典型）
        ↓
【サーバー会社】
  サイトのファイルとデータベースを置いている場所
  エックスサーバー、ロリポップなど
        ↓
【WordPress管理画面】
  記事・固定ページ・プラグインなど、サイトの中身
```

**判断の順番はいつもこれ。**

> ① 何を変更したいのか
> ② それを管理しているのはどこか
> ③ その管理画面を開く

例：「サイトの表示先を変えたい」→ WordPress管理画面を探しても DNS は変えられない。
逆に「記事を直したい」→ DNS管理画面ではなく WordPress 側。

## 1-2. 一番よくある勘違い

**ネームサーバー（NS）と DNSレコードは別物。**

```text
【ネームサーバー】= DNS設定を「どの会社が管理しているか」
        ↓ 実際の設定内容
【DNSレコード】= A / CNAME / MX / TXT などの中身
```

実例（td-group.jp）：
- ネームサーバーが `alfred.ns.cloudflare.com` / `wanda.ns.cloudflare.com`
- → **DNSの実体は Cloudflare にある**
- → サーバー（ロリポップ）側でサブドメインを作っても、Cloudflare を触らないと表示されない

「サーバー管理画面でサブドメインを作ったのにアクセスできない」の典型的な原因がこれ。

### 調べ方

| 知りたいこと | 使うもの |
|---|---|
| ドメインの登録者・ネームサーバー | WHOIS（.jp なら `whois.jprs.jp`） |
| 今そのドメインがどのIPを向いているか | `whatsmydns.net`（種別A） |
| 同上（ターミナル） | `nslookup ドメイン名` / `dig ドメイン名 A` |

覚え方は **「取得先は WHOIS、向き先は whatsmydns」**。

### ネームサーバーから管理先を判別する早見表

| Name Server の表示 | 管理先 |
|---|---|
| `uns01.lolipop.jp` など | ロリポップ |
| `dns01.muumuu-domain.com` など | ムームードメイン |
| `01.dnsv.jp` / `ns1.onamae.com` など | お名前.com |
| `ns1.xserver.jp` など | エックスサーバー |
| `〇〇.ns.cloudflare.com` | Cloudflare |
| その他 | 制作会社やクライアント独自のDNS |

# 第2部　案件着手時に必ず確認すること

作業を始める前に、以下を潰しておく。ここを飛ばすと当日に事故る。

## 2-1. サーバー

- 現在どのサーバーを利用しているか
- 移行先のサーバーはどこか
- サーバーの契約者・契約名義（**クライアント名義かどうかは重要**。設定を落とす前に一言必要）
- サーバー管理画面にログインできるか
- FTP / SFTP の接続情報
- データベースの情報

### ★ 渡されたログイン情報は「何の画面のものか」を確認する

「WordPressのログイン情報です」と渡されたものが、実際にはサーバー管理画面だった、ということが起きる（td-group で発生）。次の3点を最初に確定させる。

```text
・このID/PWは、どの管理画面のものか（サーバー / WordPress / DNS / ドメイン）
・WordPressはもう存在するのか、これから作るのか
・現行サイトは何で動いているのか（WordPressとは限らない）
```

**現行サイトがWordPressだと決めつけない。** 静的サイト、Cloudflare Pages、Wix、STUDIO など、CMSが無いケースもある。お客様からの案内文に答えが書いてあることも多いので、着手時にもう一度読み返す。

## 2-2. ドメイン・DNS

- ドメインをどこで取得・管理しているか
- **DNSをどこで管理しているか（ネームサーバーは何か）**
- 現在設定されている DNSレコード
- Webサイトとメールがそれぞれどこを向いているか
- **DNSを変更するのは誰か**（自分／制作会社／お客様）

## 2-3. Webサイト

- 何のシステムで動いているか（WordPress など）
- ファイルがどこにあるか、DBがどこにあるか
- 管理画面にログインできるか
- バックアップが取れているか

## 2-4. メール

DNSを変更する場合、Webサイトだけでなく **必ずメールへの影響を確認する。**

「Webサイトを移行したらメールが使えなくなった」は定番の事故。MX / TXT / SPF / DKIM を変更前に確認・保存しておく。

- メールはどこで動いているか（サーバー付属 / Google Workspace / 外部サービス）
- **Google Workspace など外部なら、MX を触らない限り移行の影響はない**（medi-ent がこのパターンだった）
- サーバー付属のメールを使っていて、かつメールは移さない場合 → Aレコードを新IPに向けた瞬間にメールが止まる可能性がある

## 2-5. そのまま送れるヒアリング文（サーバー・DNS担当／お客様向け）

```text
・現在ドメインはどのサーバーを向いていますか
・DNSはどこで管理されていますか（ネームサーバーは何ですか）
・DNSを変更するのは誰ですか
・今回変更するレコードはどれですか
・メールに影響するレコード（MX / TXT）は変更しませんよね
・切替の前にTTLを300秒に下げていただけますか
・切替後にSSLの発行が必要ですか
・切り戻しが必要になった場合の手順はありますか
・旧サーバーはいつまで残していただけますか
```

## 2-6. 移行案件で追加で確認すること

```text
・移行元／移行先のサーバー
・WordPressファイルとデータベース、両方の移行手順
・URL置換が必要か
・Basic認証・noindexの設定と解除タイミング
・バックアップは取得済みか
```

> 旧サーバーで改ざん・攻撃があった場合、そのまま全部コピーすると不正ファイルごと新サーバーに持ち込む。
> 「原因・影響範囲の確認 → ファイル確認 → クリーンアップ → 移行」の順で進めてもらう。

# 第3部　DNS

## 3-1. DNSとは

ドメイン名とサーバー（IPアドレス）を結び付ける住所録。

```text
example.com
   ↓ DNSに問い合わせ
「123.45.67.89 のサーバーです」
   ↓
そのサーバーに接続
```

## 3-2. 主なレコード（実務で出るのは4つ）

| レコード | 役割 |
|---|---|
| **A** | ドメイン → IPアドレス。**サイト公開で触るのは基本これ** |
| **CNAME** | ある名前を別のホスト名に紐付ける（`www` → 頂点ドメイン など） |
| **MX** | メールの配送先。**触るとメールが止まる** |
| **TXT** | SPF / DKIM / DMARC、各種所有権確認。**消すとメールが届かなくなる** |

## 3-3. 【最重要】触っていい／絶対に触らない

| | |
|---|---|
| **変更する** | `@`（またはドメイン名そのもの）のAレコード<br>`www` のAレコード（またはCNAME） |
| **絶対に触らない** | MX（メールが止まる）<br>TXT（SPF / DKIM / DMARC）<br>`mail.` `smtp.` などメール系サブドメインのAレコード<br>上記以外のすべてのレコード |

> **「Webサイトを公開するから」といって、DNS設定を丸ごと書き換えない。**

お客様に設定をお願いする場合は、この一文を必ず添える。実際にメールが止まる事故が起きるのはここ。
**作業前に現在のDNS設定画面のスクリーンショットを撮っておいてもらう**のも必須（切り戻し用）。

## 3-4. お客様に渡すレコード表の書き方

現在のネームサーバーはそのままにして、**Aレコードだけ書き換える**方式が一番事故が少ない。

| ホスト名 | 種別 | 値 | TTL |
|---|---|---|---|
| `@`（または空欄／ドメイン名そのもの） | A | 新サーバーのIP | 3600 |
| `www` | A | 新サーバーのIP | 3600 |

- 管理画面によって「@」「空欄」「ドメイン名そのもの」と表記が違う（お名前.com は空欄、さくらは「@」）
- `www` が現状 CNAME で頂点ドメインを向いているなら、そのままでOK（頂点が新IPを向けば自動で追随する）
- **「ネームサーバーを変えてください」と言われた場合は別物。** `ns1.xxxxx.jp` のようなホスト名が渡されるので、IPアドレス（Aレコード）と混同しない
- **CNAME を A に変える場合もある。** Cloudflare Pages や Netlify などで公開されているサイトからの移行では、頂点ドメインが CNAME になっていることがある。この場合は「CNAMEを削除 → Aレコードを追加」という書き方になる

### ★ レコード一覧を先にもらう

**推測で依頼を出さない。** 現在のレコード一覧をスクリーンショットで共有してもらってから、変更内容を確定させる。td-group では、一覧を見る前に判断して指示が二転三転した。一覧をもらった時点で内容は一発で確定した。

### 依頼文に必ず入れる3点

1. **実施のタイミング** — 「準備が整い次第こちらから合図しますので、それまで変更をお待ちください」。移行前に切り替えられると本番が壊れる。**この一文があると、間違いに気づいたときに撤回できる**
2. **変更しないでほしい行を名指しで列挙** — テスト環境のAレコード、Worker等で稼働中のサブドメイン、TXTレコード、MX。「その他は触らないでください」だけでは弱い
3. **変更するのはこの1行だけ**と明示

## 3-5. TTLと「DNSの浸透」

変更しても全員に即座に反映されるわけではない。一時的に「Aさんは新サイト、Bさんはまだ旧サイト」という状態が起きる。

**TTL（Time To Live）** は「この情報を何秒キャッシュしていいか」の設定値。

```text
TTL = 300    →  最大5分
TTL = 3600   →  最大1時間
TTL = 86400  →  最大24時間
```

> **切替の1〜2日前に、TTLを300秒に下げてもらう。**

これをやっておくと当日の反映が数分で済む。TTLが86400のまま当日を迎えると、切り替えても最大1日反映されず、**その後のSSL設定が当日中に終わらない**。

**日程が決まった時点でTTL変更を先に依頼するのがディレクターの仕事。**

## 3-6. Cloudflare を使っている場合

各レコードに **Proxy status** という設定がある。

| 設定 | 意味 |
|---|---|
| **DNS only**（グレーの雲） | 素通し。普通のDNSとして動く |
| **Proxied**（オレンジの雲） | Cloudflare を経由する。実際のサーバーIPが隠れる |

- テスト環境やSSL発行前は、**必ず「DNS only」**にしてもらう。Proxied のままだとサーバー側でSSL証明書を発行しようとしても認証に失敗する
- Proxied の状態で `nslookup` しても Cloudflare のIPが返るため、**本当のサーバーIPは分からない**
- Cloudflare は **メンバー招待**ができる。Members → Invite でエンジニアのメールアドレスを招待すれば、認証情報を共有せずに済む。作業後に権限を外すのも一瞬。DNS権限だけに絞った招待も可能

## 3-7. 確認コマンド

```bash
dig example.com A          # Aレコード（IPアドレス）
dig example.com NS         # ネームサーバー
dig example.com MX         # メール
dig example.com TXT        # SPF/DKIM/所有権確認
dig +short example.com     # 結果だけ簡潔に
```

**キャッシュを避けたいとき**は問い合わせ先を指定する。

```bash
dig @8.8.8.8 example.com          # Google DNSに聞く
dig @ns1.example.com example.com  # 権威サーバーに直接聞く（最速で真実が分かる）
```

Windows は `nslookup example.com`、Mac / Linux は `host example.com` でも簡易確認できる。

**レジストラ側のNS確認**（ゾーン内のNSレコードと、実際の委任先がズレることがある）：

```bash
whois example.com | grep -i "name server"
```

**伝播状況**を世界各地から見るなら `whatsmydns.net` か `dnschecker.org`。

## 3-8. DNS切替前に新サーバーの表示を確認する方法

hosts ファイルに新IPを書けば、自分のPCだけ向き先を変えられる。

```text
203.0.113.10  example.com www.example.com
```

- Mac … `/etc/hosts`
- Windows … `C:\Windows\System32\drivers\etc\hosts`

**確認後は必ず削除する。** 消し忘れて「切り替わってないですね」と誤報告するのが定番のミス。

> **「別のサブドメインが同じサーバーを向いているから、そっちで確認できる」は当てにならない。**
> td-group では `www.td-group.jp` がすでに新サーバーを向いていたので事前確認に使えると考えたが、Cloudflare のキャッシュ等の影響で表示確認には使えなかった。**素直に hosts でやるのが確実。**

# 第4部　SSL

## 4-1. 基本

`https://` の通信を暗号化する仕組み。現在のサイトは HTTPS が標準。

**多くの場合、SSL証明書は DNS切替後でないと発行できない。** Let's Encrypt 等は「そのドメインが本当にこのサーバーを向いているか」を確認して発行するため。

つまり素直にやると **「DNS切替 → SSL発行までの間、https が繋がらない時間」** が発生する。お客様への事前告知が必要。

## 4-2. ★エックスサーバーなら事前発行できる

エックスサーバーには「**他社ネームサーバーでのDNS認証**」がある。

```text
SSL設定 →「他社ネームサーバーでのDNS認証」を選択
→ 表示されたDNSレコード（TXT）を、現在のDNS管理元に追加してもらう
→ 認証が通れば、DNS切替前に証明書が発行される
→ 当日はAレコードを切り替えるだけ
```

これができると **「切替後サイトが見えない時間」がほぼゼロになる。** 移転案件では最初に検討する。

※このとき「エックスサーバーのネームサーバーへ変更」は選ばない。SSL発行前にネームサーバーを変えると一時的に表示が壊れる。

**ロリポップにはこの仕組みがない。** DNSがロリポップを向いて反映されている状態でないと証明書をインストールできない。

## 4-3. SSL発行が失敗するとき

原因はだいたいこの2つ。

1. ドメインがまだそのサーバーを向いていない（DNS未反映）
2. **そのドメインにアクセス制限やリダイレクト設定がかかっている**

2は盲点。**Basic認証をかけたままだと認証局がサイトを確認できず失敗する。** SSL発行時は一時的に解除する。

## 4-4. 反映時間の目安

| | 反映まで |
|---|---|
| エックスサーバー | 最大1時間程度 |
| ロリポップ | 5〜10分程度 |

「設定中」「反映待ち」の間にアクセスすると一時的に警告が出るが、正常な過程。

# 第5部　データ移行

## 5-1. 「ファイルをコピーしたから移行完了」ではない

WordPress は記事・固定ページ・設定情報の多くが **データベース**に入っている。ファイルとDBの両方が必要。

| 移す対象 | 中身 |
|---|---|
| **ファイル** | テーマ、プラグイン、`wp-content/uploads` の画像、`wp-config.php` など |
| **データベース** | 記事、固定ページ、各種設定（`wp_options`）、フォーム設定 |

## 5-2. 手順

### 移行前
1. 旧環境のバックアップ（ファイル＋DB）
2. 現在の設定情報を記録
3. DNS設定のスクリーンショット保存

### 移行後
1. 新サーバーへファイルを配置
2. データベースを移行
3. **DB接続情報を確認**（`wp-config.php` の内容と新サーバー側のDB情報が一致しているか）
4. 表示確認、管理画面ログイン確認
5. ページ・画像・フォームの確認

## 5-3. ★URL置換 ── 移行案件で必ず起きる

移行後、DBの中に **旧環境の絶対URLがそのまま残る。** これが td-group で実際に起きた（旧テスト環境への参照が約380箇所・57ページ）。

```bash
# まず件数だけ確認（何も書き換えない、押しても壊れない）
wp search-replace '旧URL' '新URL' --dry-run --all-tables

# 問題なければ --dry-run を外して実行
wp search-replace '旧URL' '新URL' --all-tables
```

WP-CLI ならシリアライズデータも壊さず処理してくれる。使えない環境なら **Better Search Replace** プラグインで同等のことができる（「まず変更をシミュレーションする」チェックボックスが `--dry-run` に相当）。

### 注意点

- **`http://` と `https://` の両方を別々に置換する。** td-group では `http://` 表記の分が漏れた
- **画像は先に実ファイルを新サーバーの `uploads` へコピーしてから URL置換。** 順序を逆にすると404になる
- 置換後、テーマ内の直書きURLは別途 `grep -r "旧ドメイン"` で確認
- シリアライズ等で一括置換できない箇所は、管理画面から手動更新が必要になることがある
- 置換完了後、**サイト全体をクロールして旧ドメインの文字列がゼロになったことを確認**してから旧環境を停止

### 参照残りのチェック方法

サイトマップが無い場合は WordPress REST API から URL一覧を取れる。

```bash
# 投稿・固定ページのURL一覧を取得
curl -s "http://対象ドメイン/wp-json/wp/v2/posts?per_page=100" | grep -o '"link":"[^"]*"'
curl -s "http://対象ドメイン/wp-json/wp/v2/pages?per_page=100" | grep -o '"link":"[^"]*"'
```

カスタム投稿タイプがある場合は、そのエンドポイントも忘れずに。

## 5-4. テーマだけ差し替える場合

テーマファイルのアップロードは **見た目・機能のファイルを差し替えるだけ**なので、DBに入っているコンテンツには触れない。既存の記事も問い合わせフォームの履歴も残る。

ただし、投稿タイプやカテゴリの移動が必要な場合は、リリース後に手動作業が発生する。旧側の記事はいきなり削除せず、**一旦非公開**にしておくと戻せる。

## 5-5. SMTP設定に注意

SMTP は **サイトのURLとは独立した設定**なので、URL が変わったから設定し直し、という性質のものではない。ただし確認は要る。

**SMTPの設定値も `wp_options` に保存されている** ので、旧URLの話とまったく同じ構造で、**テスト環境の設定がそのまま本番に引き継がれる。**

見るべき3点：

1. **SMTPホストがどこのサーバーか**
   - 新サーバーのもの → そのままでOK
   - 旧サーバーやテスト用のもの → 差し替えが必要
   - Gmail / SendGrid などの外部サービス → ドメイン移行の影響を受けないのでそのままでOK
2. **送信元（From）のドメインとSPF** — 送信サーバーが変わる場合は SPFレコードの確認が必要
3. **DNS切替時のMXレコード** — Aレコードだけ設定してMXを引き継ぎ忘れると、そのドメイン宛のメールが全部止まる。**サイトは正常に見えるので気づきにくく、「公開後に問い合わせが1件も来ない」で発覚する**

# 第6部　メール

## 6-1. 変更前に必ず控えるもの

- MX レコード
- TXT レコード（SPF / DKIM / DMARC）
- `mail.` `smtp.` などメール系サブドメインのAレコード

## 6-2. パターン別の影響

| メールの運用場所 | Aレコードを変えたときの影響 |
|---|---|
| Google Workspace / 外部サービス | **MXを触らなければ影響なし**（medi-ent はこれ） |
| 旧サーバー付属のメールを継続利用 | MXが向いているホスト名（例 `mail.example.com`）に**旧サーバーのIP**でAレコードを追加して固定する必要がある |
| 新サーバーへメールも移行 | 新サーバー側でメールアカウントを作成してからMXを切り替える |

## 6-3. 公開後のテスト

- 問い合わせフォームから実送信を1回
- 管理者宛の受信確認
- 自動返信がある場合は、**返信先アドレスを変更したら必ず再テスト**（td-group では返信先を変えたら自動返信が届かなくなった）
- 迷惑メールフォルダも確認

## 7-2. エックスサーバー

### 管理画面の構成

**2つの画面**に分かれている。混同すると探し物が見つからない。

| 画面 | できること |
|---|---|
| **Xserverアカウント** | 契約・支払い・ドメイン取得・サーバー移行申請 |
| **サーバーパネル** | ドメイン設定・SSL・WordPress・DB・アクセス制限など**サイトの設定全般** |

### ドメインを追加する

```text
サーバーパネル →「ドメイン設定」→「ドメインを追加」
→ ドメイン名を入力 →「追加する」
```

ドメイン追加と同時に無料独自SSLの設定も一緒に追加される（不要ならチェックを外す）。反映まで数分〜最大1時間。

> **サーバーにドメインを追加することと、DNSでアクセス先をエックスサーバーへ向けることは別作業。**
> サーバー側だけ設定しても、DNSが旧サーバーを向いていれば一般ユーザーは旧サーバーへアクセスする。

### サブドメインを作る

```text
サーバーパネル →「サブドメイン設定」
→ 名前（test など）を入力し、無料独自SSLにチェック
```

サブドメインは無料・無制限。

### WordPress

- **新規** … 「WordPress簡単インストール」。データベースも自動で作られる
- **他社サーバーからの引っ越し** … 「**WordPress簡単移行**」機能あり。移行元のPHPが5.3以降であることが条件

ロリポップ → エックスサーバーのような構成はこの機能で完結することが多い。

### SSL

```text
サーバーパネル →「SSL設定」→ 対象ドメインを選択
→「独自SSL設定追加」→ 確認画面へ進む → 追加する
```

★ **DNS切替前の事前発行**については第4部を参照。

### サーバーのIPアドレス

```text
サーバーパネル →「サーバー情報」→ IPアドレス
```

お客様にAレコードの値を伝えるときは、ここの数字を使う。

### Basic認証・アクセス制限

- **Basic認証** … 「アクセス制限」
- **特定IPを拒否** … 「アクセス拒否設定」
- **WordPress管理画面の保護** … 「WordPressセキュリティ設定」

「WordPressセキュリティ設定」には **国外アクセス制限** と **ダッシュボードアクセス制限（IP制限）** がある。

> **海外案件で注意。**
> 国外からWordPress管理画面に入れない場合、サイトの不具合ではなくこの設定が原因。海外の協力会社に管理画面を触ってもらう案件では、事前にホワイトリストへIPを登録するか設定をOFFにする。

## 7-3. ロリポップ！

### 管理画面の構成

「ユーザー専用ページ」1つにまとまっている。左メニューの分類だけ覚えておけば迷わない。

| メニュー | 主な中身 |
|---|---|
| **サーバーの管理・設定** | 独自ドメイン設定 / サブドメイン設定 / データベース / ロリポップFTP / FTPアカウント設定 |
| **サイト作成ツール** | WordPress簡単インストール |
| **セキュリティ** | 独自SSL証明書導入 / アクセス制限 |
| **メール** | メール設定／ロリポップ！webメーラー |
| **ユーザー設定** | アカウント情報 / アカウントのセキュリティ |

### 独自ドメイン・サブドメイン

```text
「サーバーの管理・設定」→「独自ドメイン設定」
「サーバーの管理・設定」→「サブドメイン設定」
```

サブドメイン作成時に **公開（アップロード）フォルダ**を指定する。このフォルダ名は後でWordPressのインストール先として使うので控える。

> **★ ロリポップ側でサブドメインを作っただけでは表示されない。**
> DNSが外部（Cloudflare など）で管理されている場合、そちらにAレコードを追加してもらう必要がある。第1部・第3部を参照。

### WordPress

```text
「サイト作成ツール」→「WordPress簡単インストール」
→ インストール先（ドメイン／サブドメイン／サブディレクトリ）を選択
→ 利用データベース：「新規自動作成」
→ サイトタイトル・ユーザー名・パスワード・メールアドレスを入力
```

「新規自動作成」を選ぶと、DB名とパスワードがランダムな文字列で自動生成される。エンジニアから「DB情報を共有してください」と言われたときに渡すのはこれ。

エンジニアに渡す一式：

```text
データベース名
DBユーザー名
DBパスワード
DBホスト（mysql84-1.lolipop.lan のような形式）
```

DBホスト名は「サーバーの管理・設定」→「データベース」で確認できる。

補足：
- ユーザー名に `admin` `test` `administrator` `root` は使えない
- インストール先に `index.html` があるとサイトが表示されない。削除かリネーム
- 複数サイト運用なら、DB名を自動生成に任せず、ドメイン名と紐づけた名前で先に作っておくと後で判別しやすい
- **DB一覧はMySQLのサーバーごとに分かれて表示される。** 見つからないときは画面を下までスクロールして他のサーバー名の見出しが無いか確認

### 一番確実なDB情報の確認方法

FTPで `wp-config.php` を見る。実際に使われているDB情報が全部書いてある。

```text
「ロリポップ！FTP」→ 対象の公開フォルダ → wp-config.php
```

```php
define( 'DB_NAME', '...' );
define( 'DB_USER', '...' );
define( 'DB_PASSWORD', '...' );
define( 'DB_HOST', '...' );
```

### SSL

```text
「セキュリティ」→「独自SSL証明書導入」
→ 対象ドメイン（wwwあり・なし両方）にチェック
→「独自SSL（無料）を設定する」
→ 5〜10分待つ →「SSL保護有効」になれば完了
```

- **DNSがロリポップを向いていないと設定できない。** 一覧でドメインが選択できない場合、まずDNSを確認
- 無料独自SSLは一度設定すると解除できない仕様なので、対象ドメインの選択は慎重に

### Basic認証（アクセス制限）

```text
「セキュリティ」→「アクセス制限」→「新規作成」
→ .htaccess設置ディレクトリ、認証フォームのタイトル
→ ユーザー名・パスワード（10ユーザーまで）
```

> **★ WordPressで使うときの注意**
> この機能は対象ディレクトリの **`.htaccess` を上書きする。**
> パーマリンク用の記述が消え、**トップページ以外が404になる**ことがある。
>
> - 設定前に `.htaccess` をダウンロードして保管
> - 設定後、WordPress管理画面の「設定 → パーマリンク」を開いて **そのまま保存**（記述が再生成される）

### サーバーのIPアドレス

管理画面にIPの表示がない。**初期ドメインから引く。**

```text
①「アカウント情報」でロリポップの初期ドメインを確認
　（例：td-web.cutegirl.jp のような形式。.webdav-lolipop.jp はFTP用なので違う）

② その初期ドメインに対してIPを引く
　nslookup td-web.cutegirl.jp
　または whatsmydns.net で種別「A」検索
```

本番ドメインで引いてもよいが、CloudflareのProxyが有効だとCloudflareのIPが返るため、**初期ドメインから引くほうが確実。**

### SMTP情報の確認

```text
「メール」→「メール設定／ロリポップ！webメーラー」
→ 対象アドレスの「確認・変更」
```

送信サーバー（SMTP）に出ている値がホスト名。標準は `smtp.lolipop.jp`、ポートは 465（SSL）か 587。

### 2段階認証（本人確認）

「普段と異なる環境からのログイン」に対して、登録メールアドレスへ認証URLが送られる。**他人がログインしようとすると必ず止まる。**

```text
「ユーザー設定」→「アカウントのセキュリティ」
→「普段と異なる環境からのログイン」の本人確認を「無効」
```

**ただし、これはアカウント単位。サブドメインだけオフにはできない。** 無効化すると本番サイトを含むアカウント全体が対象になる。

> **無効化は最後の手段。** 先に「渡すものを絞る」ことを検討する。

| エンジニアの用途 | 渡すもの |
|---|---|
| DBのインポート・書き換え | **phpMyAdmin** — DB接続情報でそのまま入れる。ロリポップのログイン不要 |
| ファイルのアップロード | **追加のFTPアカウント** — 「FTPアカウント設定」で作成。公開フォルダを限定できる。作業後は削除するだけで権限回収 |
| WordPress本体の操作 | **WordPressの管理者アカウント** — 別ユーザーを発行 |

移行作業なら、たいてい **phpMyAdmin + FTP** の2つで完結する。ユーザー専用ページに入る必要があるのは、サブドメイン作成やSSL設定などサーバー設定を触るときだけ。

**アカウントがクライアント名義の場合は、セキュリティ設定を落とす前に必ず一言入れる。**

| | |
|---|---|
| ドメイン | medi-ent.co.jp（継続） |

**当日の流れ**
```text
制作会社側で本番環境へアップ
　↓
お客様側でDNS切替（Aレコード変更）
　↓
制作会社側でSSL設定
```

**やったこと**
- お客様に渡すレコード表（`@` と `www` のAレコード）を作成
- 「絶対に触らないレコード」を明記した依頼文を用意
- 切替後、`dig` でDNS伝播を確認
- SSL設定完了を確認

**起きたこと・学び**
- **新サーバーのIPが途中で変わった。** 最初に案内した値と最終的な値が別だった → **お客様に送る前にサーバーパネルの「サーバー情報」で必ず現物を確認する**
- 制作会社の指示で、お客様へのDNS連絡は補足説明を省いて **値のみ**共有する方針になった
- 切替・SSL後に **WordPress管理画面にログインできない**事象が発生。`wp-json` は正常応答するのに `wp-login.php` が404 → **SiteGuard等のセキュリティプラグインでログインURLが変更されている**か、エックスサーバー側のログイン制限が濃厚。ブラインドで探らず、**制作会社に直接ログインURLを聞く**のが正解
- GAタグは **お客様側でGoogleアナリティクスを発行**してもらい、そのタグを制作側で設置。制作側発行だとアカウントが制作側管理になり先方が不便になるため

**エックスサーバーだったので、次回は「DNS切替前のSSL事前発行」を検討できた案件。**

## 8-2. td-group.jp（2026年8月）

**内容：** サイトリニューアル。テスト環境構築 → 本番公開。

| | |
|---|---|
| 本番 | td-group.jp |
| テスト | test.td-group.jp（ロリポップ内サブドメイン） |
| 旧テスト環境 | td-group.test-page.site |
| サーバー | ロリポップ（MySQL 8.4 / `mysql84-1.lolipop.lan`） |
| **DNS** | **Cloudflare**（NS: `alfred.ns.cloudflare.com` / `wanda.ns.cloudflare.com`） |
| サーバーIP | 初期ドメイン `td-web.cutegirl.jp` から取得 |

**起きたこと① サブドメインが表示されない**
ロリポップでサブドメインを作成し、WordPress簡単インストールも完了していたのに、ブラウザからアクセスできなかった。
→ **原因：Cloudflare側に `test` のAレコードが無かった。**
→ 対応：Cloudflare で Type=A / Name=`test` / IPv4=サーバーIP / **Proxy status=DNS only** を追加依頼。

**起きたこと② 旧テスト環境への参照が大量に残った**
先方のAIチェックで、新サイトから旧テスト環境（test-page.site）への参照が **約380箇所・57ページ**残っていると指摘された。クリックすると外部の転送ページに飛ぶ状態。

具体的な箇所：キャンペーンバナー3枚のリンク先、症状ページ26本の画像、地図画像。

対応順序（先方指示、これが正しい順序）：
```text
① 画像を新サーバーへ移設
② 57ページのリンクを一括置換
③ 参照ゼロを確認
④ 旧環境を停止
```

- `--dry-run` で件数を先に確認
- **`http://` 表記の分が漏れていた** → http / https を別々に置換
- シリアライズで一括置換できない箇所は管理画面から手動更新
- 管理画面（wp_options 等）にも旧サイトの残りがあった

**再発防止として本番前チェックに「リンク先」「旧ドメインへの参照」を追加した。**

**起きたこと③ フォーム・メールまわり**
- 問い合わせの送信先がテスト用のアドレスのままだった → 本番用に変更
- 採用応募フォームの自動返信の返信先を変更したところ、自動返信が届かなくなった → 配信先を一本化して再テスト
- SMTP情報がテスト時の暫定値のまま本番に引き継がれるリスクを事前に確認

**起きたこと④ テスト環境がhttpのまま**
test環境が https 化されておらず http で200応答していた。**本番公開時に混在コンテンツ警告が出るリスク**として事前に共有。

**起きたこと⑤ GTM・GA4の設置**
サイト側にはGTMのスニペットが入っている状態。GA4は**GTM経由で配信する方式（第12部の方法A）**を採り、GA4のスニペットはHTMLに直貼りしない方針にした。GTMのタグに測定IDを入れ、トリガーを Initialization - All Pages にして保存 → プレビューで発火確認 → 公開、という流れ。

**GTMの設定は先方指定のGmailアカウントから行う**取り決めになっており、作業直前に「そのアカウントにログインしたことがあるか」を確認された。→ **計測まわりは、着手時にアカウント名義とログイン手段を確定させておく。**

## 8-3. td-group.jp 本番公開当日（2026年8月31日）

**内容：** test.td-group.jp から本番 td-group.jp への公開。ロリポップ上に新規WordPressを用意し、そこへ移行してからDNSを切り替えた。

| | |
|---|---|
| 公開ドメイン | **td-group.jp**（`.com` ではない。社内で確認して確定） |
| 現行サイト | **Cloudflare Pages**（`td-corporate.pages.dev`）から配信。WordPressですらなかった |
| 新環境 | ロリポップ `newsite` フォルダ（初期ドメイン `td-web.cutegirl.jp` / IP `210.131.237.252`） |
| 移行元 | test.td-group.jp |
| DNS | Cloudflare |

### この日の一番の学び ── 前提が渡された情報と違っていた

朝に「WordPressのログイン情報です」として渡されたものが、実際には**ロリポップの管理画面**のログイン情報だった。さらに、そのWordPress自体が**まだ存在せず、こちら側で新規作成するもの**だった（お客様からは「ロリポップからログインしてWPを新たに作成ください」と案内済みだったが、見落としていた）。

この食い違いのせいで、午前中に何度も前提がひっくり返った。

> **★ 着手時に必ず確認する**
> - 渡されたログイン情報は **どの管理画面のものか**（サーバー / WordPress / DNS / ドメイン）
> - **WordPressはもう存在するのか、これから作るのか**
> - 現行サイトは**何で動いているのか**（WordPressとは限らない。静的サイトやCloudflare Pagesのこともある）
>
> お客様からの案内文は、後で必ず読み返す。今回、お客様の「現在のサイトはCloudflareです」という一文は最初から正確だった。**渡された情報を自分の想定で上書きしない。**

### DNS切替の内容（CNAME → A）

Cloudflare のレコード一覧をお客様から共有してもらってから内容を確定させた。**一覧を見ずに指示を出そうとして判断が二転三転したので、先にレコード一覧をもらうのが正解。**

```text
【削除】 名前: td-group.jp / タイプ: CNAME / 内容: td-corporate.pages.dev
【追加】 名前: td-group.jp / タイプ: A / 内容: 210.131.237.252
        プロキシステータス: プロキシ済み（オレンジの雲） / TTL: 自動
```

依頼文には次の3点を必ず入れた。これはそのまま次回も使える型。

1. **実施のタイミング** — 移行中に先に変えると本番が壊れるので、「こちらから合図するまで待ってください」
2. **変更しないでほしい行を名指しで列挙** — `test.` のAレコード、Worker で動いているサブドメイン、TXTレコード
3. **変更するのは1行だけ**と明示

### 頂点ドメインと www が別々を向いていた

`td-group.jp` は Cloudflare Pages、`www.td-group.jp` はロリポップ（`210.131.237.252` / プロキシ済み）と、**別々の場所を向いていた。** 現行サイトを Cloudflare Pages で作ったときに www 側を直さず残ったものと思われる。

- `www` は特別なものではなく、`test.` などと同じただのサブドメイン。片方だけ別のサーバーに向けることができる
- **公開後に、両方を新サイトへ向けてどちらかに統一（通常は www なし）し、転送をかける。** 放置すると同じ内容が2つのアドレスで見え、検索評価が分散する

### 「www で事前確認できるはず」が使えなかった

www がすでにロリポップを向いていたので、**DNS切替前の表示確認に使えると考えたが、実際には Cloudflare のキャッシュ等の影響で確認できなかった。**

> **切替前の表示確認は、素直に hosts ファイルでやるのが確実**（第3部 3-8）。「別のサブドメインが同じサーバーを向いているから確認できるはず」は、Cloudflare を挟んでいると当てにならない。

### 公開後に出た指摘

| 症状 | 内容 |
|---|---|
| **サイトアドレスが `http://`** | WordPressの設定が `http://td-group.jp` のままだった → `https://` に変更依頼 |

# 第12部　計測とSEO ── GA4 / GTM / Search Console / サイトマップ

## 12-0. 4つの関係

| | 何をするもの | IDの形 |
|---|---|---|
| **GA4** | サイトに**来た後**の行動を分析する | `G-XXXXXXXXXX` |
| **GTM** | 計測タグを管理・配信する「入れ物」 | `GTM-XXXXXXX` |
| **Search Console** | **検索側**の状況（クエリ・インデックス）を見る | プロパティ単位 |
| **sitemap.xml** | サイト内のURL一覧。Googleに構造を伝える | `/sitemap.xml` など |

```text
検索結果に出るまで        →  Search Console + sitemap.xml
サイトに来てからの動き    →  GA4
そのタグを配る仕組み      →  GTM
```

**GA4 と Search Console は見ている場所が違う。** どちらか片方では足りない。両方を連携させると、GA4の画面で検索クエリまで見られるようになる。

---

## 12-1. GA4 と GTM の役割

| | 役割 | IDの形 |
|---|---|---|
| **GA4** | サイトに来た後のアクセスを分析する | `G-XXXXXXXXXX` |
| **GTM** | 計測タグを管理・配信する「入れ物」 | `GTM-XXXXXXX` |

GTM は計測そのものはしない。**タグを管理して配信するだけ。** GA4 を GTM 経由で配信するか、直接HTMLに貼るかで、後の運用が変わる。

## 12-2. 設置方法は2択

| 方法 | やること | 評価 |
|---|---|---|
| **A. GTM経由（推奨）** | GTMにGA4タグを作り、測定IDを入れる。**GAのスニペットはHTMLに貼らない** | ◎ 一元管理できる。今後タグを追加するのが楽 |
| **B. 直貼り** | GA4のスニペットを全ページの `<head>` に貼る。GTMではGA4を触らない | △ GTMを入れている意味が薄くなる |

**GTMを導入しているなら A 一択。** サイトのHTMLに入れるのは GTM のスニペットだけでよく、GA4のコードは触る必要がない。

> **★ A と B を両方やらないこと。** GTM経由と直貼りが両方生きていると **二重計測**になり、セッション数やPV数が実態より多く出る。公開前チェックの「二重計測がないか」はこれを見ている。

## 12-3. GTM で GA4 を設定する手順（方法A）

```text
1. GTM の対象コンテナ（GTM-XXXXXXX）を開く → タグ → 新規
2. タグの種類：「Google タグ」（または「GA4 設定」）
3. タグID／測定ID：G-XXXXXXXXXX
4. トリガー：Initialization - All Pages
5. タグ名：GA4 - 設定タグ → 保存
6. プレビューで発火確認 → GA4 の DebugView にヒットが来るか確認
7. 公開
```

**6の確認を飛ばさない。** 「公開したのに数字が入っていない」の原因は、たいてい発火確認をしていないか、公開ボタンを押していないかのどちらか。

## 12-4. ディレクターとして事前に確認すること

```text
・GA4のアカウントは誰の名義で発行するか
・GTMのコンテナは誰の名義か／ログインできるアカウントはどれか
・サイトのHTMLに今すでに何が入っているか（GTMだけ？GAも直貼り？）
・旧サイトの計測タグは残っていないか
```

**アカウント名義は着手時に決める。** medi-ent では、制作側でGAを発行するとアカウントが制作側管理になりお客様が不便になるため、**お客様側でGA4を発行してもらい、そのタグを制作側で設置**する方針にした。GTM も同じで、td-group では **先方指定のGmailアカウント**からGTMを設定する取り決めだった。作業直前に「そのアカウントにログインしたことありますか」と聞かれて慌てないよう、**誰のアカウントで作業するのかを先に確定しておく。**

## 12-5. 移行・リニューアル時の注意

- 旧サイトから引き継いだテーマに **旧のGAスニペットが直書きで残っている**ことがある。`grep -r "gtag\|G-\|UA-\|GTM-"` で確認
- テスト環境で計測を止めていた場合、**本番公開時に解除を忘れない**
- GTMのプレビューモードのまま放置しない
- 公開後、**GA4のリアルタイムレポートで自分のアクセスが計上されるか**を必ず見る

## 12-7. Search Console

### プロパティの種類は2つ

| | 範囲 | 所有権確認 |
|---|---|---|
| **ドメイン** | サブドメインと http/https をまとめて見られる | **DNSのTXTレコード一択** |
| **URLプレフィックス** | `https://example.com/` のように接頭辞単位 | HTMLタグ / HTMLファイル / GA / GTM から選べる |

> **切り分けの基準：DNSを自分で触れる案件なら「ドメイン」、DNSが先方管理で触りにくいなら「URLプレフィックス」。**

`https://example.com/` と `https://www.example.com/` は URLプレフィックスでは**別プロパティ扱い**。リダイレクトで片方に寄せているなら、寄せ先だけ登録すればいい。

### DNSがCloudflareの場合の注意

ネームサーバーがCloudflareを向いているなら、**TXTレコードもCloudflare側に入れないと効かない。** レジストラ（お名前.com等）の管理画面に足しても反応がない、というのが一番のハマりどころ。

```text
Cloudflare → 対象ドメイン → DNS →「レコードを追加」
タイプ：TXT / 名前：@ / 内容：google-site-verification=... をそのまま貼る
```

- TXTはプロキシ（オレンジ雲）の対象外なので気にしなくていい
- 既存のSPF等のTXTは消さない。別レコードとして並べて追加できる
- Cloudflareは反映が速く、たいてい1〜2分で確認が通る

**Cloudflareのアカウントが先方持ちで権限がない場合は、迷わずURLプレフィックス＋メタタグ。** DNSに一切触らずに完結する。将来ドメインプロパティが必要になったら、そのときTXT1本だけ依頼すればいい。

### 所有権確認（URLプレフィックス／WordPress）

```text
① プロパティを追加 → 確認画面の「HTMLタグ」を展開
   <meta name="google-site-verification" content="AbCdEf12345..." />
② content="..." の中の文字列だけをコピー
③ SEOプラグインの認証コード入力欄に貼って保存
④ サーチコンソールに戻って「確認」を押す
```

貼り先の候補は3つ。上から順に安全。

1. **SEOプラグインの設定欄**（AIOSEO / Yoast / SEO SIMPLE PACK 等）
2. 子テーマの `header.php` の `<head>` 内
3. `functions.php` から `wp_head` にフックして出力

> **テーマに直接貼ると、テーマ差し替えや親テーマ更新のときに消える。** Googleは認証タグの有無を定期的にチェックしていて、消えると猶予期間のあと権限が失効する。**リニューアルでテーマを入れ替えたら、公開後にサーチコンソールでエラーが出ていないか必ず確認する。**

確認画面を閉じてしまった場合は、プロパティセレクタから未確認のプロパティを選び直せば再表示される。確認済み後にコードを見返すなら「設定 → 所有権の確認」。

### All in One SEO（AIOSEO）での貼り場所

バージョンによってメニュー名が違う。最近のAIOSEOは「一般設定」ではなく単に **「設定」**、その上部タブに「ウェブマスターツール」がある。

**直接URLで飛ぶのが早い。**

```text
https://サイトのURL/wp-admin/admin.php?page=aioseo-settings#/webmaster-tools
```

開いたら「Google検索コンソール」を選んでコードを貼り、保存。

### 登録後にやること

- **「設定 → ユーザーと権限」でクライアントを追加。** 所有者 / フル / 制限付きの3段階。**納品先には所有者権限を渡しておく**と、自分が抜けたあともデータが残る
- **GA4の管理画面から「Search Consoleのリンク」で連携。** GA4側で検索クエリまで見られるようになる

### リニューアル案件での扱い

- **ドメインを引き継ぐなら、旧環境のプロパティをそのまま使える**
- **テスト環境（サブドメインや別ドメイン）は登録しない。** noindexを外し忘れた状態で登録するとカバレッジがノイズだらけになる。**本番公開後に登録する**

## 12-8. sitemap.xml

### まず存在を確認する

ブラウザのアドレスバーに直接入力するだけ。ファイルをダウンロードする必要はない。

```text
https://サイトのURL/sitemap.xml
https://サイトのURL/sitemap_index.xml
https://サイトのURL/wp-sitemap.xml
```

XMLの一覧が表示されればそれがサイトマップ。3つとも404なら存在しない。

### 環境別のURL

| | サイトマップURL |
|---|---|
| WordPress標準（5.5以降） | `/wp-sitemap.xml` |
| **All in One SEO** | `/sitemap.xml` |
| Yoast SEO | `/sitemap_index.xml` |
| Rank Math | `/sitemap_index.xml` |
| Google XML Sitemaps | `/sitemap.xml` |

> **AIOSEOを入れていると、WordPress標準の `/wp-sitemap.xml` は自動的に無効化される。** 送信するのは `sitemap.xml` のほう。

WordPress標準のサイトマップでもSearch Consoleに登録できるしGoogleも認識する。ただし画像・動画のサイトマップが含まれず、priorityやlastmodの設定ができない。普通のコーポレートサイトなら標準で十分。

**Site Kit by Google はサイトマップを生成しない。** Google系ツールとの連携・データ表示に特化したプラグインなので、サイトマップが必要なら別途SEOプラグインを入れる。

### Search Console への送信

```text
サーチコンソール → 左メニュー「インデックス作成」→「サイトマップ」
→ 入力欄に sitemap.xml と入力 →「送信」
```

- **入力欄にはドメイン部分がすでに表示されている。** その後ろのパス部分（`sitemap.xml`）だけ入れる。**フルURLを貼ると二重になる**
- 送信できるのは**所有権の確認が通ってから**。未確認だとメニューがグレーアウトしている
- 投稿・固定ページの追加や更新に合わせて自動で再生成されるので、以後の手動操作は不要

### sitemap.xml が404になるとき

1. SEOプラグイン側でサイトマップ機能が有効になっているか（AIOSEO → サイトマップ → 「一般的なサイトマップ」）
2. 有効なのに404なら、**「設定 → パーマリンク設定」を開いて何も変えずに「保存」**。これで直ることが多い

パーマリンクの再保存は `.htaccess` の書き換えを促す操作なので、第11部の「下層が404」と同じ対処。

## 12-9. 公開時のSEO・計測まわり まとめ手順

```text
① 本番公開・SSL確認が終わっている
② noindex を解除する ★これを忘れると全部が無意味
③ sitemap.xml が生きているかブラウザで確認
④ Search Console にプロパティを追加（本番のみ。テスト環境は登録しない）
⑤ 所有権確認（DNS触れる→ドメイン / 触れない→URLプレフィックス＋メタタグ）
⑥ サイトマップを送信
⑦ GTM で GA4 タグを公開、DebugView でヒット確認
⑧ GA4 と Search Console を連携
⑨ クライアントに所有者権限を付与
```

# 付録A　用語早見表

| 用語 | 一言でいうと |
|---|---|
| ドメイン | サイトの住所（`example.com`） |
| URL | 部屋番号まで含めた住所 |
| サーバー | サイトのデータを置く場所 |
| IPアドレス | サーバーの実際の番地（`123.45.67.89`） |
| DNS | ドメインとサーバーをつなぐ住所録 |
| ネームサーバー（NS） | DNS設定をどこの会社が管理しているか |
| Aレコード | ドメイン → IPアドレス の指定 |
| CNAME | 名前 → 別の名前 の紐付け |
| MXレコード | メールの配送先。触らない |
| TXTレコード | SPF/DKIM等。触らない |
| TTL | DNS情報のキャッシュ時間。切替前に短くする |
| DNSの浸透 | 変更が全体に行き渡るまでの時間差 |
| Proxy status | Cloudflare特有。DNS onlyかProxiedか |
| SSL/TLS | https で通信を暗号化する仕組み |
| 混在コンテンツ | https ページ内に http のファイルが混ざった状態 |
| WordPress | サイトを管理・生成するCMS |
| データベース | 投稿・設定を保存する場所 |
| `wp_options` | WordPressの設定が入るDBのテーブル。URLやSMTPもここ |
| `wp-config.php` | WordPressのDB接続設定ファイル |
| WP-CLI | コマンドでWordPressを操作するツール |
| search-replace | DB内の文字列を一括置換するコマンド |
| SMTP | メールを送信するためのサーバー設定 |
| Basic認証 | 閲覧前にID/PWを要求する仕組み |
| noindex | 検索結果に載せない指定。公開時に解除 |
| GA4 | サイトに来た後のアクセスを分析（`G-`） |
| GTM | 計測タグを管理・配信（`GTM-`） |
| Search Console | Google検索側の状況を確認 |
| ドメインプロパティ | サブドメイン・http/httpsをまとめて見る登録方式。DNSのTXTで確認 |
| URLプレフィックス | 接頭辞単位の登録方式。メタタグ等で確認できる |
| sitemap.xml | サイト内のURL一覧をGoogleに伝えるファイル |
| google-site-verification | Search Consoleの所有権確認用のコード |

# 最後に

サーバーやDNSの設定を自分で完璧にできる必要はない。ディレクターの仕事は、

- **誰が何を管理しているかを最初に確定させること**
- **段取りの順番を間違えないこと**（TTL → バックアップ → 移行 → 確認 → DNS → SSL → 確認）
- **戻せる状態を作っておくこと**

この3つ。技術的な手を動かす部分は、エンジニアやサーバー担当に依頼して構わない。依頼するときに **何を確認して何を渡せばいいか** が分かっていれば、それがディレクションになる。
